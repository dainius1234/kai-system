## 4. Default assumption for current infrastructure

Until E0 evidence proves otherwise, the planning default becomes:

> **KEEP THE CONCEPT / CAPABILITY. CHANGE THE IMPLEMENTATION BOUNDARY ONLY WHEN THERE IS A REASON.**

A current component may be:

- retained substantially as-is;
- hardened internally;
- moved under a clearer parent responsibility;
- merged with overlapping implementation;
- split because it contains unrelated trust/failure/state responsibilities;
- wrapped by a migration shim;
- have its backend replaced;
- become a module instead of a service;
- remain a service because its isolation is useful;
- remain dormant/stubbed until prerequisites exist.

But the default is **not replacement**.

Major structural change requires evidence of one or more:

- duplicate sovereignty/authority;
- conflicting sources of truth;
- unsafe trust boundary;
- shared-fate failure;
- incorrect state ownership;
- lifecycle/deployment conflict;
- resource/hardware isolation need;
- irreducible contract mismatch;
- proven maintenance burden that cannot be fixed in place.

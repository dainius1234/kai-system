Relevant existing material includes, among others:

These are not automatically mutually contradictory. Most are different slices of the same intended organism. The problem is that without one reconciled final reference, implementation can drift between different historical abstractions.

The master-canon task is therefore **reconciliation, not invention from scratch**.

## 5. Canon hierarchy

The master canon should be a **design authority**, not evidence authority.

Once frozen:

- it defines the intended final architecture and invariants;
- implementation plans must trace to it;
- deviations require explicit decision/change control;
- repository evidence still determines whether implementation actually conforms;
- the canon cannot declare a capability live merely because the design includes it.

Thus:

`MASTER CANON = WHERE WE ARE GOING`

`REPO / TEST / RUNTIME EVIDENCE = WHERE WE ACTUALLY ARE`

Never confuse the two.

## 7. Change control after freeze

"Bible" does not mean unchangeable in the face of new evidence.

It means **stable by default and changed deliberately**.

After freeze, a canon change requires:

1. identified reason/new evidence;
2. affected invariants/components;
3. alternatives considered;
4. DeepSeek/external review when material;
5. repo feasibility review;
6. Dainius approval for consequential architecture change;
7. new version/hash;
8. migration/compatibility consequences recorded.

No silent architectural drift through opportunistic coding.

# A4 Self-Diagnosis Evolution — preserve the House-in-Order machinery

> **STATUS: FUTURE DESIGN OBLIGATION / ARCHITECTURE NOTE — NOT CURRENT PROGRAMME AUTHORITY.**
>
> This note preserves an operator-directed future use of the House-in-Order/Census machinery. It does **not** authorise A4 implementation, runtime self-repair, document mutation, or autonomy. When A4 is reached, reconcile this note against the then-current architecture, latest D-numbered decisions, frozen evidence and operator authority.

## Why this note exists

During the August 2026 House-in-Order work, Dainius identified that the machinery being built to understand repository documents, writers, references, applicability and uncertainty is useful beyond the immediate build/assurance exercise.

The long-term idea is to evolve these mechanisms into part of Kai's own **self-diagnosis / self-awareness layer** when the appropriate A4 stage is reached.

The current Census/H2 work is primarily build-time assurance machinery. **Do not assume the exact scripts should become production runtime services.** Preserve the concepts, evidence model, calibrated detectors and lessons; redesign the runtime form when A4 is actually planned.

## Core A4 idea

Kai should eventually be able to inspect his own system and answer, with evidence rather than guesswork:

- What components/files/services exist?
- What is connected to what?
- Which code or process is known to read/write a given file?
- Which relationships are proven, merely possible, or unresolved?
- What changed since the last known-good state?
- Is a change expected, stale, contradictory, or suspicious?
- Which subsystem is likely responsible for a failure?
- What evidence supports that diagnosis?
- What remains UNKNOWN?
- What safe repair options exist?
- What would each repair affect?
- What should be proposed to Dainius for approval?

In simple terms: **Kai should be able to look under his own bonnet, understand what changed, explain what may be wrong, and propose a repair without pretending uncertainty is certainty.**

## Machinery from House-in-Order worth preserving

### 1. Repository / component map

Evolve the document/reference census into a wider system map:

`component -> file -> service -> dependency -> writer/reader -> runtime evidence -> owner/authority`

The future system should understand not only Markdown but also code, configuration, models, services, workflows, generated artefacts and runtime dependencies.

### 2. Proven relationship vs possible relationship

Preserve the distinction learned here:

- `PROVEN_*` — positive evidence establishes the relationship.
- `NO_PROVEN_*` — no positive relationship has been established; **not** proof of absence.
- `UNRESOLVED` / `UNKNOWN` — evidence cannot decide.
- scoped negatives only when the search/evidence boundary is genuinely closed.

A4 must never turn "I cannot prove it" into "it does not exist".

### 3. Applicability travels with evidence

A future self-diagnostic result must carry:

- exact subject/version/tree/runtime;
- instrument/version used;
- what states were actually applicable on that subject;
- known limitations;
- confidence/evidence source;
- whether the result may be used downstream.

A diagnosis without its applicability/limitations is incomplete evidence.

### 4. Drift/change detection

Use the system map to compare a known-good state with the current state and surface changes such as:

- new/removed files or services;
- changed ownership/writer relationships;
- broken references/dependencies;
- configuration drift;
- a generated file no longer matching its producer;
- expected runtime component absent;
- unexpected component active;
- documentation or authority declarations no longer matching the implementation.

This should feed Kai's existing anomaly/world-model mechanisms rather than create a disconnected second brain.

### 5. Self-diagnosis / House Doctor integration

Existing architecture already contains self-capability mapping, anomaly detection, world-model persistence and the House Doctor concept (see D87-D89 in `DECISIONS.md`). A4 should connect repository/system evidence into that diagnostic loop.

Possible future flow:

`runtime symptom/change`
→ `system/repository map`
→ `candidate causes`
→ `evidence qualification`
→ `known vs unknown`
→ `impact/risk analysis`
→ `repair options`
→ `counterfactual/sandbox test where possible`
→ `recommendation`
→ **DAINIUS APPROVAL**
→ controlled action
→ independent post-action verification.

### 6. Explainability to the operator

The machinery must be able to translate technical evidence into plain language.

Example:

> "The memory service is failing because configuration X changed yesterday. File Y is generated by script Z. I can prove Z writes Y. The current generated value no longer matches the expected schema. I have not changed anything. Recommended fix A is lower risk than fix B."

Not:

> "Dependency graph inconsistency detected."

The technical evidence stays available underneath, but the operator gets a clear explanation first.

### 7. Suggestions, not uncontrolled self-repair

A4 self-diagnosis must not silently become self-modification authority.

Default chain:

`detect -> explain -> propose -> simulate/test -> request approval -> execute within scoped capability -> verify outcome`

Dainius remains final authority unless a later, explicit governance decision grants a narrowly bounded autonomy envelope.

### 8. Learning from previous faults

Do not merely store incidents. Preserve reusable defect shapes learned during House-in-Order, including:

- match a token and assign a meaning;
- wrong subject / self-vs-other misbinding;
- measurement environment cannot observe the claimed property;
- declared state exists but implementation cannot emit it;
- calibration does not cover a state used on real data;
- a manifest verifies stale evidence perfectly;
- a detector's denominator includes its own artefacts or prose/comments;
- context/corpus accidentally defines semantics;
- UNKNOWN silently treated as negative evidence;
- evidence binding exists but consumer enforcement does not.

A4 should use these as diagnostic anti-patterns and test-generation seeds.

## Relationship to the Evidence Plane / provenance work

The future self-diagnosis layer should not invent a parallel truth system.

It should consume/produce the same evidence concepts planned for the Evidence Plane:

`observation -> evidence identity -> subject -> claim -> qualification -> applicability -> confidence/uncertainty -> decision/proposal -> action -> outcome verification`

Where appropriate, later A4 design should reuse provenance/attestation standards already researched (W3C PROV, in-toto/SLSA-style attestations) while retaining Kai-specific semantics such as PROVEN/UNRESOLVED, contamination boundaries, operator approval and claim-scoped negatives.

## A4 acceptance principle

Do not call this self-diagnosis merely because Kai can scan files.

A credible A4 mechanism should demonstrate that it can:

1. detect a known injected fault/change;
2. identify the affected relationship/component;
3. distinguish decisive evidence from uncertainty;
4. avoid false certainty on an ambiguous case;
5. propose at least one safe response;
6. state what it cannot know;
7. preserve operator authority;
8. verify whether an approved repair actually fixed the original condition without creating a neighbouring regression.
